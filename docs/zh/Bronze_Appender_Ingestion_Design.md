# 技术设计：基于 DuckDB Appender 的高性能 Bronze 导入

## 1. 概述
当前的 Bronze 阶段导入使用 `jdbcTemplate.batchUpdate` 写入临时表，由于 JDBC 的逐行处理开销和 SQL 解析过程，性能存在瓶颈。本设计提议引入 **DuckDB 原生 Appender**，这是 DuckDB 内部最快的数据摄入路径，旨在在保持系统资源（内存/CPU）稳定的同时，最大化导入效率。

---

## 2. 技术实现：原生 Appender
我们将直接调用 DuckDB 原生驱动提供的 `DuckDBAppender` API，而非生成 `INSERT` SQL 语句。

### 2.1 执行逻辑
1.  **流式读取**：使用缓冲流（BufferedReader）逐行读取 EventLog 原始文件。
2.  **多表 Appender 池**：为每个 Bronze 事件表（如 `bronze_event_task_end`）创建专用的 Appender 实例。
3.  **预解析分流**：在 Java 层进行轻量级 JSON 校验和 "Event" 类型提取，根据类型将数据分发至对应的 Appender。
4.  **事务批处理**：将数据追加操作封装在周期性的提交（Commit）中，确保数据完整性的同时不牺牲速度。

---

## 3. 稳定性与资源控制
为防止 DuckDB 耗尽系统内存或使 CPU 过载：

### 3.1 内存管理（背压机制）
- **定量刷新**：每处理 **10,000 行** 或缓冲区达到 **5MB** 时，强制执行一次 `flush` 操作，将数据从内存刷入磁盘。
- **单应用单线程**：每个应用的数据摄入仅由单个线程执行 Appender 操作，避免并发写入导致的资源竞争和不可预测的 CPU 峰值。

### 3.2 CPU 限流
- 通过全局信号量或现有的 `transformationExecutor` 线程池，限制全系统内并发执行 Appender 的应用数量。

---

## 4. 进度掌控
准确的进度汇报是长时间导入过程中的核心用户体验。

### 4.1 基于字节偏移的计算
- 进度将基于 **文件描述符的字节偏移量（Byte Offset）** 进行计算，而非行数。
- `进度百分比 = 当前文件读取位置 / 文件总字节大小`。
- 这种方式能确保即使在单行长度差异巨大的情况下，进度条依然保持单调递增且精准反映物理读取状态。

---

## 5. 核心优势
- **极致速度**：预计吞吐量将比目前的 JDBC 批处理方式提升 5 到 10 倍。
- **内存安全**：无论日志文件多大，内存占用始终保持在配置的缓冲区大小内。
- **精准控制**：进度反馈与物理磁盘 I/O 完美对齐，实时可感。
